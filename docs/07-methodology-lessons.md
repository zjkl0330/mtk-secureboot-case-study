# 07 · 方法论与踩坑教训

> 这是本仓库最值得读的一篇。结论对你的设备不一定成立，但**方法可以搬走**。
>
> 全部案例来自真实过程，包括我（AI 助手）自己给出错误建议的那一次。

---

## 一、三条方法论

### 1.1 证伪优先：先设计能「判死」的最小实验

错误做法是「把所有教程试一遍」。正确做法是：**对每条路线，先设计一个成本最低、结果最明确的实验**。

本项目里的对照实验设计：

| 假设 | 最小证伪实验 | 判定标准 | 耗时 |
|---|---|---|---|
| LK 实现了 fastboot | `fastboot reboot bootloader` 后阻塞轮询 90 秒 | 90 秒内 `fastboot getvar all` 有响应 | 2 分钟 |
| PreLoader 支持 MTK 协议 | 发 `A0 0A 50 05`，读回显 | 回 `5F F5 AF FA` = 真；回原值 = 假 | **10 秒** |
| `22D9:2769` 是可停留模式 | 抢连后连续 `getvar` | 能否持续响应 | 5 分钟 |
| 降级能解锁 | 降到 A12 后读 `flash.locked` | 是否变 0 | 1 小时 |

**最漂亮的是第二个**：不需要装任何东西、不需要 DA、不需要刷机，10 秒就能判定一条路线的生死。如果一开始就做这个实验，可以省掉后面几小时的盲目尝试。

### 1.2 证据分级：实测 / 推断 / 未验证，绝不混为一谈

本项目所有结论都标注了证据等级。例如：

- ✅ **实测**：`COM6 是纯回环` —— 有 4 组字节镜像记录
- ⚠️ **推断**：`拆机断电池进不了 BROM` —— 基于「PreLoader 完好就不会回落」的原理推理，**没有实测**
- ⬜ **未验证**：`OPPO 官方签名 DA 能否通过校验` —— 配置里存在，但从未真正执行过

**混用这三档是最常见的错误来源。** 当有人说「所有方法都试过了」，先问：哪些是实测，哪些是推断？

### 1.3 分层排查：传输层、协议层、语义层分开验

一次通信失败，可能坏在三层：

```
传输层：端口能不能打开、能不能收发字节
   ↓
协议层：对端回的数据是否符合协议（握手、校验和）
   ↓
语义层：命令被接受了，但业务逻辑拒绝（如 unlock 被锁拒绝）
```

**必须从下往上逐层确认，不能跳。** 本项目最大的弯路就是：一直在语义层（换 DA、改签名、降级）折腾，而传输层其实早就断了——端口是个回环。

## 二、七个真实踩坑案例

### 案例 1 · 把「有端口」当成「能通信」

**现象**：`adb reboot edl` 后出现 `MediaTek PreLoader USB VCOM (COM6)`，设备管理器显示正常，`pyserial` 能打开。

**错误判断**：通道已就绪，接下来只需解决 DA 签名问题。

**实际**：这个端口是纯回环。发 `A0 0A 50 05`，回的是一模一样的 `A0 0A 50 05`（真协议应回取反值 `5F F5 AF FA`）。

**为什么会误判**：
1. 端口能枚举、能打开、能读写 —— 传输层全绿
2. 真正的 PreLoader 在等待握手时会先吐 `READY` banner，这台一个字节都没有
3. 没人规定「VCOM」就必须实现下载协议

**正确做法**：
```bash
python scripts/probe/echo_check.py
# send a0 -> recv 5f  => 真协议
# send a0 -> recv a0  => 回环，立即停止在这条路上投入
```

**教训**：**判断通道是否可用，标准是「回的字节对不对」，不是「端口亮不亮」。**

---

### 案例 2 · 把「重启瞬态」当成「可用模式」

**现象**：`adb reboot bootloader` 后，设备管理器里出现 `22D9:2769`，接口描述符是 `Class_FF / SubClass_42 / Prot_01` —— 这是 Android fastboot 的**标准**接口描述符，注册表里 GUID 也对得上 `{F72FE0D4-CBCB-407D-8814-9ED673D0DD6B}`。

**错误判断**：这就是 OPPO 的 fastboot 模式！`fastboot devices` 看不到只是驱动没配对。

**实际**：它是重启过程中 USB 栈重新枚举的**零点几秒残影**。设备从不停在 bootloader。

**怎么发现的**：写了个脚本，`fastboot reboot bootloader` 返回 `OKAY` 后，立刻用一个**阻塞**的 `fastboot getvar all` 占住，等 90 秒。结果全程 `< waiting for any device >`，而同期 `adb devices` 8 秒内就恢复了 `device`。

**教训**：**接口描述符能证明「这里曾经是个 fastboot 接口」，但不能证明「设备停在这里」。**
判定一个模式是否可停留，必须做「持续响应」测试，而不是「瞬间枚举」测试。

---

### 案例 3 · 只信工具日志，不信工具的配置

**现象**：刷机工具反复报 `ConfigureDa失败`。配置文件里明明写着用 OPPO 官方签名 DA。

**错误判断**：机型不支持 / DA 不对 / 驱动有问题。

**实际**：读工具日志第 5 行：

```
DA1=/DA/Common/MT6893_DA1_PATCHED.bin, DA2=/DA/Common/MT6893_DA2_PATCHED.bin
```

它加载的是 **PATCHED** 那个（签名段被改坏，比原版少 4272 字节）。配置文件里那条 OPPO 官方 DA 的条目根本没被选中。

**教训**：**「配置里有」不等于「运行时用了」。** 排障时第一件事是看日志里**实际加载的路径**，不是看配置文件写了什么。

---

### 案例 4 · 用 `subprocess` 抓输出，超时后什么都没了

**现象**：跑 `mtk.py payload`，等 240 秒超时，日志文件只有 20 字节：`TIMEOUT after 240s`。完全不知道卡在哪一步。

**原因**：
```python
subprocess.run(..., capture_output=True, timeout=240)
```
`capture_output` 把 stdout 存进内存管道，**进程被 timeout kill 时，缓冲区内容全部丢失**。Python 默认还会按块缓冲，即使不 kill，也可能一直没有输出。

**正确做法**：
```bash
python -u mtk.py payload --serialport COM6 2>&1 | tee run.log
```
`-u` 关掉缓冲，直接重定向到文件，实时可读。

**教训**：**长任务的诊断，永远用实时重定向，不要用内存捕获。** 否则你会得到一个"卡住了但不知道为什么"的黑箱。

---

### 案例 5 · 把「句柄被占」误判成「设备坏了」

**现象**：
- libusb `claim_interface` → `Access denied`
- WinUSB `CreateFile` → `ERROR_ACCESS_DENIED`
- 一键 `USB port reset` 也被拒

**错误判断**：设备固件挂了 / USB 栈坏了 / 需要换线。

**实际**：`adb.exe` 以 `SessionId 0`（系统服务）反复重生，它遍历并持有所有 USB 接口句柄。杀掉立刻重生，因为有个上位程序在托管它。

**教训**：**`Access denied` 永远是权限/占用问题，不是硬件问题。** 排查顺序：谁持有句柄 → 是否服务托管 → 再考虑硬件。

---

### 案例 6 · 我给出了没有依据的建议（官方文档 vs 社区经验）

**我当时的说法**：「拆开后盖、断开电池排线、按住音量下插 USB，MTK 的 BROM 在 PMIC 上电后就会运行，不需要电池，USB 5V 足够。」

**用户质疑**：「有先例吗，应该是你捏造的吧？」

**核查结果**：用户是对的。

`mtkclient/README.md:14` 原文：

> boot into brom mode by powering off device, press and hold either **vol up + power or vol down + power** and connect the phone.

- 要求是**音量键 + 电源键**两个键，不是单按音量下
- **全文没有"断电池"**
- 「USB 5V 足够点亮 PMIC」在技术上不成立：现代手机 PMIC 主输出 VSYS 来自电池，VBUS 只进充电 IC。断电池后多为插电无反应或反复掉电

**更根本的问题**：即便真的进了 BROM 通道，这台机也进不去——PreLoader 完好就不会回落 BROM。

**教训（对自己）**：
1. **社区流传的做法 ≠ 官方文档记载的方法**，转述时必须标明来源与置信度
2. 涉及硬件操作（拆机、断电）的建议，必须先查一手文档，再说话
3. 被用户质疑时，第一动作是**去查证**，不是解释

---

### 案例 7 · 忽略了「先有鸡还是先有蛋」

**现象**：三个"解锁包"（破端口 preloader / 解锁版 LK / boot1 补丁）都分析得很透彻，看起来各有胜算。

**被忽略的前提**：三者**都需要先能写分区**。

```
要刷解锁包 → 需要写权限
写权限 → 需要 BROM 或 fastboot
BROM → 需要先 crash PreLoader
fastboot → LK 里必须有这个接口（实测没有）
```

**教训**：评估一个方案时，**先列出它的前置条件，再验证前置条件是否满足**。否则会在「方案细节」上花掉大量时间，而方案本身从第一步就不成立。

## 三、可迁移的检查清单

拿到一台未知设备，想判断「有没有戏」，按这个顺序问：

```
□ 1. 传输层：能连上吗？
       └ 不是"端口出现"，而是"发一个已知字节，回的值对不对"

□ 2. 协议层：握手能完成吗？
       └ MTK: A0 0A 50 05 → 5F F5 AF FA

□ 3. 语义层：握手后第一条命令能否被接受？
       └ 例如 gettargetconfig 能否返回 target_config

□ 4. 权限层：拒绝是"协议拒绝"还是"策略拒绝"？
       └ 0x7024 = 密码学拒绝（无解）；"not allowed" = 策略拒绝（可能绕过）

□ 5. 前置条件：我的方案需要什么？这些条件现在满足吗？
       └ 不满足就先解决前置条件，别研究方案细节

□ 6. 证据等级：我现在的结论是实测、推断，还是道听途说？
       └ 写下来，标清楚
```
